# Migración a Firebase — 02. Security Rules

Reglas desplegadas en `firestore.rules` (+ `firestore.indexes.json`, `firebase.json`, `.firebaserc`) contra el proyecto `prodeus-app`. Ya están **live** en la base Firestore recién creada (no hay datos ni tráfico todavía, así que el deploy es de bajo riesgo).

## Helpers (equivalentes a las funciones `security definer` de Postgres)

| Firestore rule                     | Reemplaza                                                                                                                                                                                |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `isSuperadmin()`                   | `public.is_superadmin()` — 1 lectura a `users/{uid}` en vez de `profiles`                                                                                                                |
| `isGroupMember(groupId)`           | `public.is_group_member(group_id)` (migración 005, resolvía recursión infinita) — acá no hay recursión posible porque `members` es subcolección de `groups`, no se referencia a sí misma |
| `isGroupLeader(groupId)`           | `exists (select 1 from groups where leader_id = auth.uid())` inline en varias policies                                                                                                   |
| `tournamentIsActive(tournamentId)` | `exists (select 1 from tournaments where status='active')` inline en `teams`/`matches`                                                                                                   |

## Decisión de diseño que necesita tu confirmación

**Endurecimiento en `users.role`**: agregué una restricción que no existía en la RLS original — un usuario no puede modificar su propio campo `role` (solo un superadmin puede). Es una corrección de un hueco de seguridad real en el sistema actual (`profiles_update_own` no restringía columnas), no un cambio de comportamiento funcional para el usuario común. Lo dejé activo por default. Decime si:

- **(a)** lo dejamos así (recomendado), o
- **(b)** preferís paridad exacta con Supabase por ahora y lo evaluamos después.

## Costo de lecturas a tener en cuenta (Fase 4 / performance)

Varias reglas hacen `get()` sobre otro documento (`isSuperadmin`, `isGroupMember`, `isGroupLeader`, `tournamentIsActive`). Cada `get()` dentro de una regla cuenta como una lectura de Firestore facturable, además de la lectura del documento principal. Para las colecciones de alto tráfico (`predictions`, `matches`) esto puede duplicar/triplicar las lecturas por request comparado con Postgres (donde el RLS corre server-side sin costo por fila). No es bloqueante, pero es algo a monitorear una vez migrado el tráfico real — si se vuelve un problema, la mitigación estándar es mover el rol a **Custom Claims** del ID token (evita el `get()` a `users/{uid}` en cada request, que es el más frecuente).
